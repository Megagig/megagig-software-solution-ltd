# architecture.md — Megagig Website — Grit Triple Architecture

> Scaffolded with: `grit new megagig-site --triple --next`
> Reference: https://gritframework.dev/docs/concepts/architecture-modes/triple

## 1. Why Triple

The site has two genuinely different audiences with two different interfaces: anonymous visitors (public marketing site) and internal Megagig staff (content/lead management). Triple gives us that separation for free — `apps/web` (public, SEO-critical, SSR) and `apps/admin` (internal, behind auth, DataTable/FormBuilder generated) — both backed by one Go API that is the single source of truth. This also means the admin panel can be locked down (basic auth / IP allowlist / separate subdomain) without touching the public site's deploy.

## 2. Stack

| Layer | Choice | Notes |
|---|---|---|
| Backend | Go + Gin + GORM | `apps/api` — handler → service → model, per Grit convention |
| Database | PostgreSQL 16 | production; SQLite for local/dev if preferred, Postgres in docker-compose for parity |
| Cache / queue | Redis 7 | response caching + asynq job/cron queue |
| File storage | S3-compatible (MinIO dev, Cloudflare R2 or AWS S3 prod) | case-study images, product screenshots, team photos, blog cover images, résumé uploads (careers) |
| Email | Resend | lead notification emails, visitor confirmation, contact-form replies |
| Public frontend | Next.js (App Router) | `apps/web` — SSR/ISR for SEO on marketing pages |
| Admin frontend | Next.js (App Router) | `apps/admin` — Grit's Filament-like DataTable/FormBuilder resource system |
| Shared types/validation | `packages/shared` | Zod schemas + TS types, generated by `grit generate` / `grit sync` |
| Styling | Tailwind CSS + shadcn/ui | tokens from `ui-tokens.md`, rules from `ui-rules.md` |
| Auth | JWT (Grit built-in) | single `admin` role sufficient for v1; public site has no auth |

## 3. System boundaries — rules the agent must never violate

1. **API routes contain no UI logic.** `apps/api` returns JSON only. No HTML rendering, no markdown-to-HTML conversion for display purposes (raw content goes out; rendering happens in the frontend).
2. **Agent/generated code never imports from `apps/web/components` or `apps/admin/components` into `apps/api`, and never the reverse.** The only shared surface is `packages/shared`.
3. **Handlers are thin.** A handler parses the request, calls exactly one service method, and returns the standard JSON envelope. No GORM calls inside `internal/handlers/`.
4. **Business logic and all GORM queries live in `internal/services/`.** Pagination, filtering, and sorting logic belongs here, not in handlers or frontend code.
5. **No hard-coded copy or config values that belong in `SiteSettings`.** Contact email/phone/WhatsApp number, hero headline/subhead, and pricing-category blurbs must be read from the `SiteSettings` singleton resource, not hard-coded into `apps/web` components.
6. **No hard-coded colors, spacing, or font sizes.** Every value must reference a CSS variable defined in `packages/shared/themes` per `ui-tokens.md`. A raw hex code or magic pixel value in a component is a defect, not a style choice.
7. **The public site (`apps/web`) never calls the database directly and never embeds a service-role/admin credential.** It only talks to the Go API over REST with, at most, a public/anonymous-scoped token where needed (e.g. submitting a lead is an unauthenticated `POST`, rate-limited).
8. **`apps/admin` is the only app allowed to call authenticated/protected routes.** Public marketing pages only ever call `public` route group endpoints (case studies, products, testimonials, team, FAQs, blog — all read-only, published-only).
9. **New content types are modeled as resources via `grit generate resource`, not as ad hoc hand-written CRUD.** This keeps `packages/shared`, the admin pages, and the API handlers all in sync automatically.
10. **Every resource that has a `published` boolean must be filtered server-side (`WHERE published = true`) in the public service methods** — never filtered client-side in `apps/web`. Unpublished content must never reach the public bundle.
11. **File uploads always go through `internal/storage` presigned URLs.** No base64 blobs in request bodies, no files written to local disk in production.
12. **Emails are always sent through `internal/mail` (Resend), never inline SMTP calls scattered in handlers.** New email templates live in `internal/mail/templates/`.
13. **Marker comments (`// grit:models`, `// grit:handlers`, `// grit:routes:*`, `// grit:schemas`, `// grit:types`, `// grit:api-routes`, `// grit:resources`) are never hand-edited out of order or duplicated.** Always let `grit generate` inject; if manual edits are unavoidable, preserve the marker line exactly.
14. **`apps/web` route groups keep their intended chrome.** `(marketing)` pages always render inside the shared navbar+footer layout; nothing in `(marketing)` is allowed to render a bare/full-bleed page. There is no `(app)` signed-in customer area in this project — do not scaffold one (see build-plan.md, this is Triple used in "marketing + internal admin" configuration, not SaaS-with-customer-accounts).

## 5. Data flow (typical: visitor submits a quote request)

1. Visitor fills the form on `apps/web` `/start-project`.
2. Client-side validation via `CreateLeadSchema` (Zod, from `packages/shared/schemas/lead.ts`).
3. React Query mutation → `POST /api/v3/leads` (unauthenticated, public route group, rate-limited by IP).
4. Gin router → CORS middleware → rate-limit middleware → `CreateLead` handler.
5. Handler parses JSON via Gin binding tags → calls `leadService.Create()`.
6. `leadService.Create()` inserts the `Lead` row (status defaults to `new`), then enqueues two async jobs via `internal/jobs`: send internal notification email (to Megagig's inbox) and send visitor confirmation email — both through `internal/mail` (Resend).
7. Handler responds `201 Created` with the standard envelope; `apps/web` shows a success state / redirects to a thank-you view.
8. The new `Lead` appears in `apps/admin` → Leads resource on next load (or immediately if the admin dashboard has React Query polling/refetch-on-focus enabled).
9. Staff update the lead's status in `apps/admin`; this is a protected route (`PATCH /api/v3/leads/:id`), JWT-verified, admin-role-only.

For **read paths** (Home fetching case studies, products, testimonials, FAQs, site settings): `apps/web` calls `GET /api/v3/<resource>?published=true` public routes, which are wrapped by the Redis cache middleware (short TTL, e.g. 60s) since this content changes infrequently and traffic is public/anonymous.

## 6. Database schema (core models)

All models include `ID (uuid)`, `CreatedAt`, `UpdatedAt`, `DeletedAt` (soft delete) unless noted.

**User** (admin/staff accounts) — `Name`, `Email` (unique), `PasswordHash`, `Role` (`admin`), `LastLoginAt`.

**Lead** — `Name`, `Email`, `Phone`, `Company`, `ProjectType` (enum, matches service slugs), `BudgetRange` (enum), `Message` (text), `Source` (enum: `start_project` \| `contact` \| `pricing_cta` \| `home_cta`), `Status` (enum: `new` \| `contacted` \| `quoted` \| `won` \| `lost`), `InternalNotes` (text, nullable).

**CaseStudy** — `Slug` (unique), `ClientName`, `Tagline`, `CategoryTags` (string array / join table), `StatusBadge` (e.g. `"Live in production"`), `HeroImageID` (→ Upload), `Problem` (rich text), `WhatWeBuilt` (rich text), `Result` (rich text), `TechStack` (string array), `TestimonialID` (→ Testimonial, nullable), `Published` (bool), `SortOrder` (int).

**Product** — `Slug` (unique), `Name`, `Tagline`, `Description` (rich text), `FeatureBullets` (string array), `LiveURL`, `DocsURL` (nullable), `ScreenshotIDs` (→ Upload, many), `Published` (bool), `SortOrder` (int).

**Testimonial** — `QuoteText` (text), `AuthorName`, `AuthorRole`, `CompanyName`, `CompanyURL`, `AvatarID` (→ Upload, nullable), `CaseStudyID` (→ CaseStudy, nullable), `Published` (bool), `SortOrder` (int).

**TeamMember** — `Name`, `Role`, `PhotoID` (→ Upload), `LinkedInURL`, `GitHubURL`, `Published` (bool), `SortOrder` (int).

**JobOpening** — `Title`, `Department`, `Location`, `EmploymentType` (enum: full_time \| internship \| contract), `Description` (rich text), `ApplyURL` (or `ApplyEmail`), `IsOpen` (bool).

**BlogPost** — `Slug` (unique), `Title`, `Excerpt`, `CoverImageID` (→ Upload), `Body` (markdown/MDX text), `AuthorID` (→ User or TeamMember), `Tags` (string array), `PublishedAt` (nullable timestamp — null = draft), `SEOTitle`, `SEODescription`.

**FAQ** — `Question`, `Answer` (rich text), `Published` (bool), `SortOrder` (int).

**SiteSettings** (singleton — single row, no CRUD list) — `ContactEmail`, `ContactPhone`, `WhatsAppNumber`, `Address`, `SocialLinks` (JSON: linkedin, github, youtube, facebook, twitter/x), `HeroHeadline`, `HeroSubhead`, `PricingBlurbs` (JSON, keyed by service slug).

**Upload** — Grit's built-in file model: `URL`, `Key`, `MimeType`, `SizeBytes`, `UploadedByID`.

## 7. Ports & URLs (dev)

Same as Grit default (see Grit docs) — API `:8080` (+ GORM Studio at `/studio`), Web `:3000`, Admin `:3001`, Postgres `:5454`, Redis `:6380`, MinIO `:9002`/`:9003`, Mailhog `:1025`/`:8025`.

## 8. Deployment

- **Recommended for this project:** Together — `apps/web` and `apps/admin` deploy all the projects using Docker compose to Coolify, `NEXT_PUBLIC_API_URL` pointed at the API host); `apps/api` deployed via `grit deploy` or `docker-compose.prod.yml` to a VPS. This gets the public marketing site edge caching for SEO performance while keeping the Go API + Postgres + Redis + MinIO under Megagig's own infrastructure control (same pattern already used for `pharmacycopilot.com.ng` and `businesscopilot.com.ng`, so ops knowledge transfers).
- `apps/admin` should sit on its own subdomain (e.g. `admin.megagig.com.ng`) and, at minimum, be excluded from search-engine indexing (`robots.txt: Disallow: /` on that subdomain) in addition to JWT auth.
